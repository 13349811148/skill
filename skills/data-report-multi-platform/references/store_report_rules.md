# 店铺维度日报规则（已与用户确认）

一行=日期+平台+店铺，输出只包含“①平台日报”。不沿用模板示例数据。原26列顺序保持，在最后增加第27列“店铺净利润”；汇总商品日报同日同店净利润，包含空烧推广，缺失规则见货品与利润规则。

| 列 | 规则 |
|---|---|
| 日期/平台/店铺 | 当日业务日期与真实平台/店铺 |
| 填报人 | references/store_report_config.json 固定配置；梦仲瑶食品旗舰店（拼多多）=陈飞；其他未配置店铺留空并记录 |
| 访客数 | 后台整店当日访客，不用曝光、点击、订单数代替；不累加商品访客 |
| 曝光次数/点击次数 | 仅推广口径，全店托管+商品推广合计；不当作整店自然流量 |
| 支付金额 | 按原始订单支付日去重汇总商家实收金额(元)，不从商品日报有效成交结果反推；已退款订单的原支付保留，退款另按事件日扣减 |
| 支付订单数 | 按原始订单支付日去重订单号，沿用已确认的指定订单排除；不用商品行数/件数代替 |
| 支付买家数 | 支付日去重支付买家数；脱敏手机号/昵称不能当可靠买家标识 |
| 退款金额/退款订单数 | 只统计退款成功，按售后编号去重金额、订单编号去重退款单数；按同意退款时间归日并标注估算，包含历史支付订单退款；申请时间不作为退款日 |
| 新客数/老客数/老客数占比 | 占比取后台原值；老客数=ROUND(支付买家数×老客占比,0)，新客数=支付买家数−老客数；人数是用户确认的推算值，来源写入独立日志 |
| 客单价 | 支付金额÷支付订单数 |
| 支付转化率 | 支付买家数÷访客数 |
| 净成交额 | 当日订单商家实收金额−当日退款成功金额（同意退款时间归日，估算）；允许负值 |
| 推广花费 | 账户当日总花费，包含两类推广。禁止重复叠加账户总计与商品明细 |
| 推广成交额 | 推广净成交额，优先账户后台“净交易额(元)” |
| 推广ROI | 全店净成交额÷推广花费；不是推广净成交额÷推广花费 |
| 推广费比 | 推广花费÷全店净成交额 |
| 店铺评分/投诉差评数 | 有后台明确数据才填，否则留空，不自行合并可能重叠的投诉/差评 |
| 今日主要动作/异常说明 | 始终留空；诊断只写独立日志 |

所有公式所需输入缺失或分母为0时结果留空。全店净成交额<0时ROI和费比均留空。净成交额=0且花费>0时ROI为0，费比分母为0留空；花费=0且净成交额>0时费比为0，ROI分母为0留空。

## 输入与可追溯性

`build_store_report.py` 读取 `--input` 或数据库下 `店铺日报输入`、`店铺数据`、`7.店铺数据库` 的 CSV/XLSX。一行是完整店铺日汇总，必须提供“日期、平台、店铺”。CSV为UTF-8。只映射明确的原始指标，不从同名商品汇总或推广数据当作整店数据。

标准原始列：访客数、推广曝光次数、推广点击次数、支付金额、支付订单数、支付买家数、退款金额、退款订单数、推广花费、推广净成交额、店铺评分、投诉差评数。店铺可用“店铺名称”。金额单位为元。未知保持空白，真实0写数字0。后台支付/退款及订单数只作复核，不再填报为计算来源；原始订单及售后来源优先于所有后台金额。输入不含示例值或未标口径的商品有效销售额。字段来源保留在 `<输出名>_生成日志.json`，每字段采用最新来源；同一最新来源内冲突的日指标报错而不盲加。多文件若覆盖不同渠道或店铺，先按实际口径整理再传入，不能直接平均比例或累加去重人数。

自动读取 `4.推广数据库`/`推广数据` 下“账户每日汇总”XLSX，并使用同名 `.xlsx.archive.json` 的 `shop`（必要时 `platform`）确定来源。账户记录必须无商品ID。读取总花费、净交易额、曝光量、点击量，按最新导出覆盖相同店铺日指标，不与商品明细累加。非账户渠道的数据应先标准化。

按用户2026-11-09最新确认，订单商家实收用于支付金额，退款成功记录按同意退款时间归日，明确为估算。缺支付时间、同意退款时间、退款成功状态或金额时不猜填；未知退款不能当0。旧的“仅用后台金额、不用同意退款时间”限制已由本次规则替代。详见store_cashflow.md。

## 推广商品分摊与店铺汇总的区别

商品推广保留原始实际花费（稳定成本推广归入商品推广）。全店托管总花费=账户当日总花费−当日商品推广实际花费；只在全店托管商品中按成交金额占比分摊，按分取整并调整尾差保证总额一致。相同商品同时存在两类推广时分开核算再合并，托管ROI/每笔成交成本标识为核算估算。账户总费在店铺日报只取一次，不把分摊结果重复相加。总费负差、托管花费>0但托管成交额=0时必须报出不能分摊，不能随意分配。

## 运行

`python scripts/build_report.py --start-date YYYY-MM-DD --end-date YYYY-MM-DD --store-input <标准化店铺日指标.csv>`

默认额外输出店铺日报。仅店铺：加 `--store-only`。店铺字段缺失不阻塞其余字段输出，单独日志列出原因。商品日报继续受原营销/成本与异常订单规则约束，不能声称商品报告已成功。

## 2026-10-24 补齐数据接入

后台“梦仲瑶食品官方旗舰店”与订单/推广“梦仲瑶食品旗舰店（拼多多）”已由用户确认为同店。配置别名关联，填报人为陈飞。新增读取 `7.后台数据库` 的已归档工作簿和 `.archive.json` 店铺元数据；按日选择最新来源。交易概况的成交金额、订单数、退款金额/单数仅用于订单售后现金流复核；成交买家数、流量等非金额指标仍按原规则映射。退款成功记录按同意退款时间估算归日。

访客数仍缺少时留空，不从买家数/四舍五入转化率反推；支付转化率可保留后台明确给出的当日原始值，后续补齐真实访客后优先按原公式算并核对。平台展示的客单价按买家计算，与本日报已确认的金额÷订单数不同，仍按确认公式重算。

“店铺评分”填综合体验星级，不把百分比评价排名或3.8分服务体验分冒充星级；“投诉差评数”填有明确日期筛选的新增差评条数，本批口径1至3星且不含默认评价，日志注明不含未知投诉数。后台归档的新/老买家数源自比例推算；按用户确认的规则重新推算并记录来源，不冒称原始人数。运营动作和异常说明继续留空。

运行商品日报时适配V3编号目录、重复空表头及XLSX维度异常；不修改原始数据。拼多多推广按最新完整店铺日商品快照与账户日总额分别选取，严格保留商品推广实际花费，仅托管商品按成交金额占比分摊，逐日核对。缺少营销/成本且用户允许先填已知字段时，可添加 `--allow-missing-reference`，相关成本、活动、补贴及利润留空；数据无效及小额订单确认门槛不跳过。

“本周”默认本周一至昨日的完整日；如果用户明确要今天，仅有部分数据也可按实际覆盖生成并日志注明。缺某天源数据不得伪造为0。

## 原始访客数补齐（2026-10-24）
读取后台归档的流量数据表：访客数只取店铺访客数（人），不取商品访客数或浏览量。以支付买家数÷店铺访客数计算支付转化率，并与后台原始显示值按百分比两位小数核对；不从转化率反推访客。访客数跨日相加只表示日访客累计，不能表述为周去重人数。


## 新老客人数（用户确认，2026-10-24）

读取后台老买家占比原值；老客数=支付买家数×占比，采用十进制四舍五入至整数；新客数=支付买家数−老客数。不要用取整后人数反算并覆盖原始占比。任一输入缺失时两个人数都留空；已知0和100%合法，比例越界、支付买家非整数则报错。人数的推算性质写入独立日志，不写入用户要求留空的“异常说明”。保留公式，使买家数或占比变更时人数同步重算。
